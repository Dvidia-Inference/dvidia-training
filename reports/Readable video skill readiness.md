# Turn Robot Videos Into Trustworthy Skills

As of 26 October 2026, DVIDIA should present an uploaded clip as a **reviewable visual goal proposal** and make the evidence boundary visible at every step. The current caller-calibrated RGB path can propose a planar destination for a supported proxy and invoke an authored PiPER simulator controller; it does not recover a human action sequence, metric depth, contact, or a learned motor policy. That narrow path is useful groundwork because the proposed goal is reproducible and can be tested against an independent task scorer, but the reported pilot still has a gap between installed goals and oracle goals. The next research step should be a deliberately staged, single-task action-learning study: first establish an oracle-action synthetic benchmark and outcome scorer, then replace selected authored decisions with a learned action model using synchronized action-bearing data. Make the UI explain what it knows, what the user supplied, and what remains unobserved. **No result in this report qualifies a real arm or supports deployment.**

## RGB can propose goals, while actions need additional evidence

A plain RGB video can show appearance and a visible endpoint, but it does not uniquely identify metric depth, camera-to-robot coordinates, forces, friction, stable grasp, or a feasible command for another gripper. These are different unknowns: a calibration supplied by the caller resolves a declared mapping assumption, while action and contact evidence require their own measurements. DVIDIA’s current video-goal package appropriately records the supplied orthographic calibration and video digest, and refuses unsupported profile/runtime combinations; its green proxy and planar task limits are part of the method, not interface details to hide. The candidate’s PiPER controller uses privileged simulator state, so a successful run demonstrates authored goal execution under that simulator setup rather than learning from the video. ([DVIDIA install guide](../docs/video-goal-install-v01.md))

Research systems that bridge human demonstrations to robots make the missing inputs concrete. UMI records synchronized RGB, gripper pose, continuous jaw width, and common-frame calibration with a handheld gripper; it filters trajectories for the target robot’s kinematics. The paper also reports that frame calibration mattered: in one cup task, absolute actions succeeded in 5/20 trials versus 16/20 for delta actions, with the authors attributing the gap likely to calibration bias. ([UMI paper](https://arxiv.org/abs/2402.10329)) DexMV instead uses two RGB-D views, 3D hand/object estimates, retargeting, and a defined Adroit-hand simulator task. Human2Sim2Robot gets a one-demonstration result by extracting object pose trajectory and pre-contact hand pose from RGB-D, then training with simulation RL and a task digital twin. These papers show viable routes, not evidence that arbitrary monocular clips can be converted directly into portable robot skills. ([DexMV paper](https://arxiv.org/abs/2108.05877), [Human2Sim2Robot paper](https://proceedings.mlr.press/v305/lum25a.html))

The product implication is to keep the first upload workflow local and explicit. Let the user select a named task/profile, review the object and goal, and confirm a calibration overlay with axes, units, coverage, and uncertainty. Preserve source timestamps/hash, calibration, edits, and outcome annotations in a versioned sidecar. Ask users to label the result and any failure or recovery; show “not observed” for unavailable depth, contact, force, or action.

## Trust depends on an independent task predicate

A visually plausible final frame is not sufficient proof that the task succeeded. Define the task predicate before inference and score it independently from the proposal or controller that produced the result. For placement, the predicate might separately require the correct object, a pose inside a target region, support and settling, and retention after release. RGB can contribute identity and appearance evidence; metric position requires calibrated depth or known geometry; interaction claims need robot/gripper telemetry or explicit contact sensing. If evidence is occluded, stale, inconsistent, or absent, the result should remain “unverified” and execution should abstain when the missing evidence matters.

This separation follows published evaluation practice. VP² evaluates video prediction by downstream closed-loop planning and simulator-state task success, and reports that common perceptual/video metrics do not reliably track execution performance. A robot success-detection study found transfer across environments challenging and visual variation more damaging than language variation, which argues against a universal image-only verifier. ([VP² paper](https://arxiv.org/abs/2304.13723), [AAAI success-detection study](https://ojs.aaai.org/index.php/AAAI/article/view/30552)) DVIDIA’s own v0.1 benchmark already demonstrates why the distinction matters: the roadmap reports 6/8 intended-task completions for installed goals versus 8/8 for oracle goals, while replaying the demonstrated endpoints also scores 8/8 on a separate endpoint measure. The endpoint result therefore cannot stand in for task completion. These are project results from four synthetic videos and two new starts each, not a learned-policy or generalization claim. ([DVIDIA roadmap](../docs/roadmap.md))

The UI should show “goal detected,” “calibration needs review,” “evidence incomplete,” or “task predicate verified in simulation,” with a short explanation of the evidence. Label simulator oracles clearly. Report false-completion rate among verified outcomes, success recall when evidence is sufficient, abstention coverage, per-condition counts, and latency on named hardware. Freeze thresholds on development cases before held-out confirmation; the literature provides no universal thresholds for DVIDIA’s task.

## Replace authored decisions one bounded step at a time

The next research step is a complete evidence contract for one rigid block-placement task, followed by synthetic branches that test whether the benchmark can detect action understanding. Branch actions from identical states, score object outcomes independently, and compare the authored controller, oracle actions, a small learned action model, and shuffled/open-jaw/no-op controls. Use short bounded action chunks and fresh held-out layouts.

Recent OpenWAM work provides a useful pattern: counterfactual action branches from matched contexts can test whether a model distinguishes action-dependent futures. The paper reports forward-dynamics outcome identification rising from 21.1% to 71.3% among 16 same-state outcomes under its LIBERO study, while separately reporting policy success. That is a benchmark result for that system, not an expected DVIDIA result or proof of physical transfer. ([OpenWAM paper](https://arxiv.org/abs/2610.07922)) DVIDIA should first use simulator-oracle actions so every branch has a known intended action and reference outcome; then fit a compact action-conditioned outcome model or policy and measure whether it beats shuffled controls on frozen starts. Only after that should it test human action records. A model that predicts outcomes is still not a controller, and a controller that passes simulation still is not physically qualified.

The roadmap below distinguishes project proposals from evidence already available. Acceptance gates are proposed research decisions; they are not claims about achieved performance.

## Physical interaction evidence is the deployment gate

Useful human-video transfer remains task-, embodiment-, and data-specific. UMI’s handheld gripper captures actions directly; DROID records synchronized robot episodes with cameras, depth, calibration, and interaction data. Neither shows that an ordinary upload identifies motor commands. ([UMI paper](https://arxiv.org/abs/2402.10329), [DROID paper](https://arxiv.org/abs/2403.12945)) For a first data pilot, use one task and PiPER simulation, complete demonstrations, and retained failures. Twelve attempts across demonstrators or reset sessions is a proposed format/review pilot size, **not a sufficiency threshold**. Preserve timestamps, calibration, object track, proxy/end-effector pose, jaw opening, phase, observed contact/hold/release, and outcome. Do not infer force, slip, or contact from RGB.

Before deployment, require a physical capture study on a selected arm/gripper. Calibrate camera/base and tool frames; record commanded and observed joint/jaw response, timing, sensor age, and measured contact/load response; retain failures and recoveries; score outcomes independently. Compare simulation with measured motion/contact, define the operating envelope, then run supervised physical qualification with a frozen candidate and protocol. If hardware is unselected, this gate remains future work. Capturing physical data alone does not qualify a skill.

## Conclusion: advance through three evidence gates

The product can feel simple when it asks users only for decisions that materially resolve uncertainty: name the task, confirm the visual target, review calibration, and say whether the demonstrated attempt succeeded. The system should then preserve a clear lineage from video to proposal to simulator result. Reusable skills emerge by adding action and outcome evidence task by task, not by upgrading an endpoint detector’s label. Keep every artifact bound to its profile, calibration, task predicate, dataset/protocol hashes, and qualification scope.

1. **Prioritize a local readiness and verification pilot.** Add reviewed calibration/goal overlays and independent task-predicate scoring to the supported planar block task. Run held-out occlusion, wrong-object, offset, near-miss, and absent-object cases; establish false-completion and abstention behavior before showing a verified state.
2. **Run the oracle-action synthetic benchmark.** Branch oracle actions from matched simulator starts, compare against the authored controller and shuffled/no-op/open-jaw controls, and independently score every outcome. Then replace only a bounded decision with a learned candidate and test on frozen starts. Treat this as the next direct experiment toward reusable learned skills.
3. **Require a physical-data capture gate before deployment.** After choosing a real arm/gripper, collect synchronized calibrated visual and action telemetry with measured actuator/contact observations and complete outcomes; quantify simulator residuals and run separate supervised hardware qualification. Until these gates pass, describe the output as a simulation candidate, never as a real-arm-qualified skill.
