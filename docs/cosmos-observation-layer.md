# Cosmos as an optional PiPER observation layer

This is a research design, not an integration claim. NVIDIA’s October 2026 Cosmos release includes two potentially relevant paths: **Sim-Bimanual** predicts video observations conditioned on an initial image and robot/camera actions, while **Sim-Transfer** renders RGB from simulator controls such as depth or segmentation. Neither function is itself a video-to-action extractor or a PiPER policy. The Sim-Bimanual model card currently lists AgiBot as its supported embodiment and describes 16B parameters; adapting to PiPER would require a separately validated embodiment/action mapping and post-training. [Project page](https://research.nvidia.com/labs/cosmos-lab/cosmos-simulation/) · [Sim-Bimanual model card](https://huggingface.co/nvidia/Cosmos3-Nano-Sim-Bimanual) · [Cosmos repository](https://github.com/NVIDIA/cosmos)

## Bounded experiment

Keep MuJoCo as the source of physical state, contacts, action execution, and outcome scoring. For each frozen scene and action sequence, save native RGB and paired depth/segmentation controls. An optional offline worker may generate observations with Sim-Bimanual, or appearance-varied RGB with Sim-Transfer. Link each output to its native episode, timestamps, camera, embodiment, actions, goal, and physical ground truth. First audit visual alignment with actions fixed. In a separate closed-loop comparison, give the same frozen policy native or generated views, allow its actions to differ, and score both with native physics. No current state-only learner measures visual transfer.

Audit generated views against the native state for object and goal visibility, object/goal localization error, mask and depth alignment where those controls are supplied, collision/contact scene consistency, and consistency with the conditioning action. Then report policy action-following, goal precision, false completion, and native task success separately. Explicitly count missing or obscured objects, visually plausible but physically unsupported contacts, and false-finished appearances. A generated frame is evidence about a visual observation only; it never overrides native collision or completion ground truth. Because video generation may drift or hallucinate, compare paired frames throughout the rollout and retain failures rather than filtering them out.

The project page reports 166 ms latency for Sim-Bimanual on one GB300 GPU and 240 ms for Sim-Transfer on one GB200 GPU. These are model-specific reported figures, not measured PiPER control-loop latency or CPU performance. The current Sim-Bimanual embodiment listing is AgiBot, so no PiPER support or transfer should be assumed. [Cosmos project performance and model descriptions](https://research.nvidia.com/labs/cosmos-lab/cosmos-simulation/) · [Model card hardware and embodiment details](https://huggingface.co/nvidia/Cosmos3-Nano-Sim-Bimanual)

## Future artifact contract

An optional offline worker would need a versioned input/output bundle containing: native RGB, depth, and segmentation streams; timestamps and frame rate; camera intrinsics/extrinsics and coordinate convention; synchronized robot actions with named embodiment and action schema; task goal; native simulator states and contact/outcome labels; and hashes for the source episode, simulator, assets, model checkpoint, and generation settings. Store generated frames and their timestamps beside the source, linked by episode and frame IDs. Validate alignment before a generated view can enter training or evaluation, and keep its provenance visible to downstream consumers.

This note proposes data collection and evaluation only. It does not download or execute Cosmos, change the current CPU behavior-cloning benchmark, or claim Cosmos can control this PiPER model.
